## Where the AI was wrong or unhelpful
1. **Premature Slot Release on HTTP 504 (Ambiguity Bug):**
   - *AI Output:* The initial code generated by the AI treated HTTP 504 Gateway Timeout identically to HTTP 503, immediately rolling back the lead's state to `PENDING` and freeing the tenant concurrency slot.
   - *How I caught it:* Reviewing `assignment-b-workflow/mock_telephony/server.py`, I observed lines showing that the server simulates both a 2% *pre-placement* 504 (where the call was never placed) and a 4% *post-placement* 504 (where the call was placed and dialed, but the response timed out). If the dispatcher freed the slot on 504, it would cause `tenant_concurrency_exceeded` and `concurrent_dial_same_phone` violations.
   - *Fix:* I overhauled the error handler: on 504 or network timeout, the lead remains locked in `RESERVING` while an async task queries `GET /v1/calls?request_id={request_id}` to resolve whether the call exists before releasing or confirming.
2. **Wall-Clock Assumptions & Boundary Drift:**
   - *AI Output:* The AI generated window checks using standard Python `datetime.now()` with a static offset computed once at boot.
   - *How I caught it:* Under 600× simulation speed, system scheduling delays of even a few milliseconds caused calls near the 21:00 or 18:00 cutoff to arrive past the provider's grace period.
   - *Fix:* I implemented local linear extrapolation `sim_epoch + (wall_now - real_epoch) * speed` synced periodically from `/v1/clock`, and added a mandatory pre-flight check in `dispatch_call()` immediately prior to issuing the HTTP POST request.
